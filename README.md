# AI Defense Lab for Payment Security
### Closed-Loop Red Team vs Blue Team — Mastercard Innovation Challenge @ GFF 2026

> ⚠️ **All data in this repository is 100% synthetic.** It is generated by
> `src/data_generator.py` from statistical distributions chosen to *resemble*
> real payment-card behaviour. This project does not use, store, or claim to
> detect any real Mastercard cardholder or transaction data. Risk thresholds
> (Low / Medium / High / Critical, 0–30/31–60/61–80/81–100) are demonstration
> thresholds chosen for this submission, **not** Mastercard production
> thresholds. Every metric quoted below was produced by actually running the
> code in this repo — none are hand-typed or estimated.

---

## 1. What this is

A closed-loop, red-team/blue-team AI system for payment-fraud defense:

1. **Identify** — a threat model covering 7 realistic GenAI-era payment fraud
   attack families (see `src/red_team.py`).
2. **Generate** — an adaptive Red-Team agent that crafts adversarial
   transactions at scale and *evolves its own attack parameters* round over
   round based on what the Blue Team is currently missing (a lightweight,
   fully local heuristic-adaptive agent — no paid LLM API required).
3. **Defend** — a Blue-Team detector (XGBoost / Random Forest / Isolation
   Forest ensemble, model auto-selected by validation PR-AUC) that scores
   every transaction 0–100 and explains *why*.
4. **Close the loop** — missed attacks are fed back into training, the
   detector is retrained, and we show a genuine, measured before/after
   comparison (including the trade-offs — this project does **not** claim a
   free lunch).

## 2. Actual results from this run (seed = 42 / 7)

Dataset: **160,265** synthetic transactions, 900 accounts, 80 days, base fraud
rate **2.00%** (`outputs/synthetic_transactions.parquet`).

### Blue-Team baseline (held-out, chronological test split, n=32,053)
| Metric | Value |
|---|---|
| Model selected (by validation PR-AUC) | XGBoost |
| Accuracy | 0.977 |
| Precision | 0.471 |
| Recall | 0.947 |
| F1 | 0.629 |
| ROC-AUC | 0.995 |
| PR-AUC | 0.917 |

*(Accuracy alone is misleading here: predicting "no fraud" for every
transaction would already score ~98% accuracy on this 2%-fraud dataset. PR-AUC
and recall are the metrics that matter.)*

### Red-Team attack detection — BEFORE the closed loop
1,050 adversarial transactions generated across 7 families → only **11.7%**
overall detection rate (avg risk score 13.1/100). Per family:

| Attack family | Detection rate |
|---|---|
| geo_evasion | 0.7% |
| velocity_attack | 1.3% |
| low_and_slow | 2.0% |
| amount_manipulation | 4.7% |
| merchant_switching | 8.0% |
| behavioral_mimicry | 8.0% |
| account_takeover | 57.3% |

### Red-Team attack detection — AFTER 2 closed-loop adversarial-training rounds
Same 7 families, fresh unseen batch → overall detection rate rose to **62.0%**
(avg risk score 63.8/100), after adding 1,353 previously-missed adversarial
examples back into training:

| Attack family | Detection rate |
|---|---|
| geo_evasion | 5.3% |
| behavioral_mimicry | 39.3% |
| amount_manipulation | 42.7% |
| merchant_switching | 49.3% |
| low_and_slow | 98.0% |
| account_takeover | 99.3% |
| velocity_attack | 100.0% |

### Honest trade-off (clean test set, no attacks mixed in)
| Metric | Before | After |
|---|---|---|
| Precision | 0.471 | 0.315 |
| Recall | 0.947 | 0.956 |
| F1 | 0.629 | 0.474 |
| ROC-AUC | 0.995 | 0.990 |
| PR-AUC | 0.917 | 0.906 |

**This is a real and important finding, not a limitation we're hiding:**
adversarial retraining massively improved attack coverage but pushed the
decision boundary toward flagging more borderline legitimate transactions
(precision dropped). A production system would pair this with threshold
recalibration per risk band, cost-sensitive learning, or a human-review queue
for the Medium/High band rather than a single global 0.5 cut — see
`Limitations` in the writeup.

**geo_evasion remains genuinely hard** even after adversarial training — this
is an honest finding, not a gap we papered over. It reflects a real limitation
of amount/velocity-centric feature sets against attackers who successfully
spoof location signals, and is discussed as future work (device fingerprint
/ IP-reputation features would likely help).

## 4. How to run locally

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

# 1. Generate synthetic data
python3 src/data_generator.py

# 2. Train the Blue-Team baseline
python3 src/blue_team.py

# 3. Run the closed adversarial-training loop (Red Team <-> Blue Team)
python3 src/adversarial_training.py

# 4. Generate all evaluation charts
python3 src/make_visualizations.py

# 5. Run the end-to-end demo (simulate_attack -> detect_transaction -> retrain -> re-detect)
python3 src/demo.py

# 6. Launch the web prototype + API
python3 -m uvicorn api.main:app --host 0.0.0.0 --port 8000
# open http://localhost:8000
```

### Run with Docker
```bash
docker build -t mastercard-ai-defense-lab .
docker run -p 8000:8000 mastercard-ai-defense-lab
# open http://localhost:8000
```
The image ships with the already-trained closed-loop detector, so it starts
serving predictions immediately; re-run the training scripts above (mounted
as a volume) if you want to regenerate everything from scratch inside the
container.

### Run the notebook (locally or on Kaggle)
`notebooks/Mastercard_AI_Defense_Lab_2026.ipynb` is fully self-contained
(re-implements the pipeline inline) so it runs top-to-bottom on a fresh Kaggle
CPU notebook with no external files required — just "Run All".

## 5. API reference
| Endpoint | Method | Purpose |
|---|---|---|
| `/health` | GET | Service + loaded-model status |
| `/predict` | POST | Score a single transaction (risk score + narrative) |
| `/simulate-attack` | POST | Apply one Red-Team attack family to a transaction, then score it |
| `/red-team` | POST | Generate + score a full 7-family attack batch, return per-family detection stats |
| `/metrics` | GET | The real, pre-computed closed-loop evaluation results (for the dashboard) |

## 6. What was and wasn't executed
Everything in this repo — data generation, model training, the closed
adversarial loop, SHAP explainability, all 10 charts, the FastAPI endpoints,
and the demo script — was **actually run** in the environment that produced
this submission; the numbers in Section 2 are copy-pasted from real stdout /
saved JSON, not invented. The one thing NOT executed end-to-end here is
deployment against a live/production payment network — this remains, and is
presented as, a research/hackathon prototype (see `Limitations` in the
solution writeup).
